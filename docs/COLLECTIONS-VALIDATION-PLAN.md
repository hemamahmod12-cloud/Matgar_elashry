# خطة التحقق من Collections قبل تفعيل `COLLECTIONS_BACKEND_ENABLED`

## الهدف

التأكد من أن البيانات المرحّلة من `storeData/*` إلى `stores/main/*` كاملة وصحيحة، وأن البيع والاسترجاع والمخزون والمزامنة تعمل قبل تحويل التطبيق إلى backend الجديد.

> **قاعدة أمان:** لا تغيّر `COLLECTIONS_BACKEND_ENABLED` إلى `true` في `main` قبل اكتمال جميع مراحل هذه الخطة. بيانات `storeData/*` القديمة يجب أن تبقى محفوظة أثناء فترة التحقق.

## الحالة الحالية

- تم تنفيذ الترحيل الإنتاجي بنجاح.
- تم نقل 819 منتجًا، و47 فاتورة، و213 حركة مخزون، و21 تصنيفًا، و5 مستخدمين، وموردين اثنين.
- العداد التالي للفواتير: `1042`.
- التطبيق ما زال يعمل على backend القديم لأن العلم مغلق.
- بيانات `storeData/*` لم تُحذف.

## المرحلة 1: فحص marker والعدد الإجمالي

تحقق من وجود مستند الترحيل:

```text
stores/main/_migrations/legacy-store-data-v1
```

ويجب أن تكون حالته:

```json
{
  "status": "completed"
}
```

| `stockMoves` | 213 |
| `categories` | 21 |
| `users` | 5 |

| `expenses` | 1 |

أي اختلاف يعني **إيقاف التفعيل** والتحقيق أولًا.

## المرحلة 2: فحص سلامة الحقول

### المنتجات

لكل منتج يجب التأكد من وجود:

- `id` غير فارغ.
- `name` غير فارغ.
- `qty >= 0`.
- `sellPrice >= 0`.
- `barcode` لا يتكرر بين المنتجات النشطة.

### الفواتير

لكل فاتورة يجب التأكد من وجود:

- `id`.
- `invoiceNo`.
- `date`.
- `items` كمصفوفة غير فارغة.
- `total >= 0`.
- `paymentMethod`.
- كل `productId` داخل عناصر الفاتورة يشير إلى منتج موجود.

### حركات المخزون

لكل حركة يجب التأكد من وجود:

- `id`.
- `productId`.
- `qty > 0`.
- `type` من القيم المسموحة: `in`, `out`, `adjust`.

### المستخدمون

- يجب أن يظل `id` مساويًا لـ Firebase Auth UID.
- يجب ألا يتغير `authEmail` للمدير.
- لا تُنشئ حسابات Auth جديدة أثناء الاختبار.

## المرحلة 3: تحقق قراءة فقط من Firebase

نفّذ فحصًا إداريًا read-only من بيئة موثوقة أو Workflow مؤقت. لا تستخدم صلاحيات المتصفح ولا تضع Service Account داخل المستودع.

الفحوص الأساسية:

1. قراءة `stores/main/products`.
2. قراءة `stores/main/sales`.
3. قراءة `stores/main/stockMoves`.
4. قراءة `stores/main/users`.
5. قراءة `stores/main/settings/main`.
6. قراءة `stores/main/invoiceCounters/main`.
7. قراءة marker الترحيل.

يجب حفظ نتيجة الفحص كـ artifact، وليس رفع بيانات العملاء أو نسخة الفواتير الكاملة إلى Git.

## المرحلة 4: نشر Cloud Functions قبل اختبار البيع

شغّل Workflow النشر اليدوي للوظائف:

```text
GitHub → Actions → Deploy Cloud Functions → Run workflow
```

بعد النشر تأكد من وجود:

- `processSaleRequest`
- `processReturnRequest`

لا تختبر بيعًا حقيقيًا في هذه المرحلة. استخدم Firebase Emulator أو بيئة اختبار منفصلة كلما أمكن.

## المرحلة 5: اختبار القواعد

استخدم `firestore.rules.next` في Emulator، وليس مباشرة على الإنتاج في البداية.

اختبارات السماح المتوقعة:

| العملية | النتيجة المتوقعة |
|---|---|
| مستخدم مصادق يقرأ المنتجات | مسموح |
| مستخدم مصادق يقرأ الفواتير | مسموح حسب القاعدة |
| مستخدم غير مصادق يقرأ Collections | مرفوض |
| مستخدم يكتب مباشرة فاتورة نهائية | مرفوض أو غير متاح حسب التصميم |
| مستخدم ينشئ `saleRequests` | مسموح وفق القاعدة |
| مستخدم يستدعي Cloud Function | مسموح إذا كان مستخدمًا نشطًا |
| مستخدم يغير مستخدمًا آخر | مرفوض |
| مستخدم يحذف سجلًا مرحّلًا | مرفوض |

لا تستبدل `firestore.rules` الحالية في الإنتاج إلا بعد نجاح اختبار Emulator ومراجعة فروق القواعد.

## المرحلة 6: اختبار التطبيق على نسخة فرع

> **تنبيه مهم:** `src/collections-repository.js` يستخدم حاليًا `STORE_ID = 'main'`. لذلك لا تفعّل العلم في Preview مع اختبار بيع حقيقي، لأن الكتابة ستصل إلى متجر الإنتاج. استخدم Firebase Emulator، أو أضف أولًا إعدادًا لبيئة اختبار مثل `window.__MATGAR_STORE_ID__ = 'staging'` مع نشر Functions وقواعد متوافقة.

أنشئ فرع اختبار من آخر commit، وعدّل العلم في الفرع فقط:

```js
const COLLECTIONS_BACKEND_ENABLED = true;
```

ثم اختبر النسخة المنشورة على رابط Preview أو بيئة منفصلة، وليس على رابط العملاء الأساسي.

### اختبار الدخول

- تسجيل الدخول باسم `manager1`.
- التأكد من بقاء UID والبريد الداخلي كما هما.
- التأكد من تحميل المنتجات والمستخدمين والإعدادات.
- فحص Console وعدم وجود `permission-denied` أو `null.value`.

### اختبار المنتجات

- البحث بالاسم.
- البحث بالباركود.
- إضافة منتج اختباري.
- تعديل السعر والكمية.
- تسجيل حركة إدخال.
- تسجيل حركة إخراج.
- التأكد من ظهور التحديث على جهاز اختبار ثانٍ.

### اختبار الفاتورة

استخدم منتجًا اختباريًا أو فاتورة اختبارية:

1. إضافة منتج إلى السلة.
2. إنهاء البيع.
3. التأكد من إنشاء مستند واحد في `sales`.
4. التأكد من خصم الكمية مرة واحدة فقط.
5. التأكد من إنشاء `stockMoves`.
6. التأكد من زيادة العداد مرة واحدة فقط.
7. إعادة تحميل الصفحة والتأكد من بقاء الفاتورة.
8. الضغط مرتين بسرعة على زر البيع والتأكد من عدم إنشاء فاتورتين.

### اختبار الاسترجاع

1. فتح الفاتورة الاختبارية.
2. تنفيذ الاسترجاع مرة واحدة.
3. التأكد من إعادة الكمية للمخزون.
4. التأكد من إنشاء حركة `in`.
5. التأكد من وضع `returned: true`.
6. محاولة الاسترجاع مرة ثانية والتأكد من رفضها.

### اختبار Offline Queue

- افصل الشبكة.
- أنشئ عملية بيع اختبارية.
- تأكد من حفظها محليًا في الطابور.
- أعد الاتصال.
- تأكد من ترحيلها مرة واحدة فقط.
- لا تحذف العملية من الطابور إلا بعد نجاح الخادم.

## المرحلة 7: مقارنة قبل وبعد

قبل تفعيل الإنتاج، احفظ تقرير مقارنة يحتوي على:

- عدد المنتجات قبل وبعد.
- عدد الفواتير قبل وبعد.
- مجموع الفواتير حسب اليوم.
- مجموع قيم الفواتير حسب اليوم.
- كمية كل منتج قبل وبعد.
- رقم العداد قبل وبعد.
- عدد حركات المخزون قبل وبعد.
- قائمة أي عناصر مفقودة أو مكررة.

يجب أن تكون الفروقات المتوقعة فقط:

- حقول `migration`.
- `migratedAt`.
- معرفات الموردين التي كانت بلا `id`.
- اختلاف ترتيب العناصر، وليس محتواها.

## المرحلة 8: تفعيل تدريجي

بعد نجاح المراحل السابقة:

1. انشر Cloud Functions.
2. انشر قواعد Collections بعد مراجعتها.
3. فعّل العلم في فرع اختبار.
4. راقب الاختبارات والـConsole.
5. فعّل العلم في `main` بcommit مستقل.
6. راقب أول عمليات البيع والاسترجاع.
7. لا تحذف `storeData/*` لمدة لا تقل عن فترة مراقبة كاملة.

### التراجع

إذا ظهر خطأ:

```js
const COLLECTIONS_BACKEND_ENABLED = false;
```

ثم ادفع commit التراجع. لا تحذف Collections الجديدة ولا `storeData` القديمة أثناء التحقيق.
